B.E. Final-Year Project · Storage Engine Internals

How KiwiDB stores data, fast and without losing it.

KiwiDB is a log-structured merge-tree (LSM) key-value store written in Python. This guide takes you from "what is a key-value store?" all the way to compaction, process pools, and the theory an examiner will probe — one idea at a time, with a diagram for each.

Write-optimised Crash-safe (WAL) Async-first Python 3.12+
01

The big picture: a database that is really good at writing

At its heart, KiwiDB does something simple: you give it a key and a value, and later you ask for the value back by its key. That's a key-value store — think of a giant dictionary, or the contacts app on your phone: "Aarav" → his phone number.

▪ In plain words

A key-value store is a dictionary that survives crashes and is far bigger than your computer's memory. The hard part isn't the dictionary — it's making it durable (never loses data) and fast even when it holds far more data than fits in RAM.

Why not just use a Python dictionary?

A dict is perfect until two things happen. First, it lives only in RAM — pull the power plug and it's gone. A database must keep your data safe on disk. Second, RAM is small and expensive; real datasets are hundreds of gigabytes. So the data has to live on disk, and only a slice of it can be in memory at any moment.

Why not just append every write to one file?

Appending to a file is the fastest way to write — the disk head never jumps around, it just keeps adding to the end (a sequential write). The catch: to read a key you'd have to scan the entire file from start to finish — that's O(n), unusably slow once the file is large.

This is the central tension of all storage engines:

Fast writes want…

To just append data to the end of a file and move on. No searching, no shuffling.

Fast reads want…

Data kept sorted and indexed, so any key is found in a few jumps.

The conflict

Keeping data sorted on every write means shuffling the file constantly — which destroys write speed.

The Log-Structured Merge-tree (LSM) is one clever answer. Its bet: make writes sequential and cheap now, and pay a small, batched cost later to keep reads fast. Concretely:

  1. Buffer recent writes in a small, sorted, in-memory table (the memtable) — writes touch only RAM, so they're instant.
  2. When that table fills up, dump it to disk in one go as a sorted file (an SSTable). Sequential, fast.
  3. Never edit those disk files in place. To "update" a key you just write a newer version; to "delete" you write a marker. Old versions are cleaned up later.
  4. A background job called compaction merges the sorted files together, throwing away the dead versions and keeping reads efficient.
◆ Why it matters

LSM trees power Cassandra, RocksDB, LevelDB, HBase, ScyllaDB and the storage layer of many cloud databases. They are the standard choice for write-heavy workloads — logging, metrics, messaging, time-series. Knowing why is exactly what an examiner wants to hear.

02

Core LSM-tree concepts

Five ideas carry the whole design. Once these click, every later section is just detail.

1 · Append-only, sequential writes

KiwiDB never goes back and edits data in the middle of a file. New data is always added — to the end of the log, or as a brand-new file. Sequential writes are dramatically faster than scattered random writes on both spinning disks and SSDs, because there's no seeking and the operating system can batch them.

2 · Data has two homes: memory and disk

MemTable — in memory

A sorted, in-RAM table holding the most recent writes. It's the only part you can write to. Small (tens of MB), fast, and rebuilt from the WAL after a crash.

SSTables — on disk

Sorted String Tables: files of key-value pairs stored in sorted order. Once written they are immutable — never changed, only created and deleted.

3 · Immutability is a feature, not a limitation

Because an SSTable never changes after it's written, KiwiDB gets a lot for free: readers never need locks (the bytes can't move under them), the file can be safely memory-mapped and cached, and a crash can never leave a half-edited file. To change data, you simply write a newer version elsewhere.

▪ In plain words

Updating a key doesn't overwrite the old value — it writes a new one with a higher sequence number. Deleting a key writes a special "tombstone" marker. The newest version always wins on read; the dead ones are swept away during compaction.

4 · Levels: L0 → L1 → L2 → L3

SSTables are organised into numbered levels. Fresh flushes land in L0. As data accumulates, compaction merges it down into L1, then L2, then L3 — each level holding roughly 10× more data than the one above it. Higher-numbered levels are bigger, older, and more tidy (fully sorted with no overlaps).

5 · Compaction keeps it all from rotting

Without cleanup, the disk would fill with duplicate and deleted keys, and reads would have to check more and more files. Compaction is the background merge that takes several sorted files, merges them into one, drops superseded versions and expired tombstones, and writes the tidy result one level down.

The price of the design: three "amplifications"

Every storage engine trades off three costs. Examiners love these terms, so learn them as a set:

AmplificationPlain meaningIn an LSM tree
WriteHow many times one logical write gets re-written to disk.Higher — a record is written once on flush, then re-written each time compaction moves it down a level.
ReadHow many places you might have to look to answer one read.Higher — a key could be in the memtable or any level, so reads may probe several files (bloom filters tame this).
SpaceExtra disk used beyond the live data.Higher temporarily — dead versions & tombstones linger until compaction reclaims them.
★ If the examiner asks…

"What does an LSM tree trade away for fast writes?" → It accepts higher write, read, and space amplification. Compaction is the mechanism that pays down read and space amplification, at the cost of more write amplification. That single sentence shows you understand the whole trade-off.

Go deeper: why does writing more actually make things faster?

It sounds backwards — LSM writes data several times (flush, then each compaction) yet is praised for write speed. The trick is what kind of writes they are. The user-facing write only touches RAM and a sequential log append, both nearly free. The extra writes happen in the background, in big sequential batches, off the critical path of your request. So the user sees low latency, while the expensive-but-batched re-writing is hidden. A B+ tree, by contrast, does a random-access write synchronously on the user's path. Trading random writes for batched sequential ones is the whole game.

03

The data structures, one at a time

KiwiDB is really a small toolbox of classic data structures, each chosen for one job. We'll take them in the order data actually flows through them: from the in-memory skip list, through the log and on-disk tables, to the structures that make reads fast.

3.1 · The skip list — the memtable's engine

in memory  app/memtable/skiplist.py

The memtable must keep keys sorted (so flushing produces a sorted file) and allow fast insert, update and lookup while many writers hammer it at once. KiwiDB uses a skip list — a sorted linked list with extra "express lanes" stacked on top.

▪ In plain words — the highway analogy

Imagine a highway where the bottom lane stops at every town (every key, in order). Above it sit express lanes that skip most towns. To find a town you ride the highest express lane until the next stop would overshoot, then drop down a lane and repeat. You zoom past most of the list and arrive in about log(n) hops instead of checking every node.

Each node is given a random height when created (the _random_level method): roughly half the nodes reach level 1, a quarter reach level 2, and so on. That probabilistic shape is what gives the express lanes their balanced, no-rebalancing-needed structure — unlike a balanced tree, you never have to rotate or rebuild anything.

How it stays correct with many writers at once

This is the cleverest part of KiwiDB and a likely viva target. Multiple async tasks can write simultaneously, so the skip list uses fine-grained, per-node locking rather than one big lock:

  • Reads take no locks at all. A get just walks the pointers. A node becomes visible to readers only after a fully_linked flag is set as the last step of insertion, so a reader never sees a half-linked node.
  • Inserts lock only the handful of nodes they touch — the predecessors at each level of the new node — not the whole list. Other writers working elsewhere proceed in parallel.
  • Locks are always acquired in a fixed order (ascending Python id() of the nodes). Consistent ordering is the textbook way to make deadlock impossible.
  • Validate-then-retry. After locking, the insert re-checks that the predecessors still point where it expects. If another writer slipped in, it releases and retries. This is optimistic concurrency — assume no conflict, verify, redo on the rare clash.
★ If the examiner asks…

"Why a skip list and not a balanced tree (like a red-black or AVL tree)?" → Skip lists give the same O(log n) search but are far simpler to make concurrent: insertion only relinks a few pointers, so fine-grained locking and lock-free reads are easy. Balanced trees need rotations that can ripple across the structure, which is painful to lock correctly.

3.2 · The MemTable — active table plus a flush queue

in memory  app/memtable/, app/engine/memtable_manager.py

There are two flavours of memtable, managed together:

Active memtable

The single writable skip list. Every put and delete lands here first. It tracks its own size and entry count.

Immutable queue

When the active table is full it is frozen and moved into a short queue (up to 4 tables) awaiting flush. Frozen tables are read-only sorted lists — searched by binary search.

When the active table crosses its threshold (counted as entries in dev mode, bytes in prod mode), the manager freezes it: it snapshots the data, pushes the frozen table onto the queue, and starts a fresh empty active table — so writes never block waiting for a flush. If the queue is already full, new writes feel gentle backpressure (they wait, with a timeout) until the flush pipeline drains a slot. A read checks the active table first, then the queued tables newest-first, so the most recent value always wins.

3.3 · The Write-Ahead Log (WAL) — the safety journal

on disk  app/wal/writer.py

The memtable lives in RAM, so a crash would erase every write that hadn't been flushed yet. The WAL prevents that. Before a write touches the memtable, it is appended to the WAL on disk. If the process dies, KiwiDB replays the WAL on startup to rebuild the exact memtable that was lost.

▪ In plain words

The WAL is like jotting a task in your notebook before you start doing it. If you're interrupted, the notebook tells you exactly what was in progress so you can finish it. "Write-ahead" literally means: write to the log ahead of changing anything else.

Each record is stored in a self-describing frame so a half-written tail (from a crash mid-append) can be detected and ignored:

WAL frame:  [ 4-byte length ] [ msgpack payload ] [ 4-byte CRC32 ]
            └ how many bytes  └ the key, value,    └ checksum — if it
              follow            seq, timestamp        doesn't match, stop

On replay, KiwiDB reads the length, reads that many bytes, and verifies the CRC32. A mismatch means the log was truncated by a crash, so replay stops cleanly at the last good record. Once a memtable is safely flushed to an SSTable, the WAL is truncated (old entries dropped by writing the survivors to a temp file and atomically swapping it in) so the log never grows without bound.

3.4 · The SSTable — sorted, immutable, on disk

on disk  app/sstable/writer.py, reader.py

An SSTable isn't one file — it's a small folder of four files that together make a key fast to find without reading the whole table:

Why store records sorted?

So lookups can binary-search and so two SSTables can be merged in one linear pass (the basis of compaction).

Why blocks?

Disks read in chunks. Grouping records into ~4 KB blocks means one read fetches many records, and the cache can hold whole blocks.

Why CRC on every record?

Disks bit-rot and crashes truncate. The checksum lets a read detect corruption instead of returning garbage.

3.5 · The Bloom filter — "is this key definitely not here?"

per SSTable  app/bloom/filter.py

A read might have to check many SSTables. Most of them won't contain the key — so opening and scanning them is wasted work. A bloom filter is a tiny, probabilistic gatekeeper that answers one question very fast: "could this key be in this table?"

▪ In plain words — the bouncer analogy

A bloom filter is like a club bouncer with an imperfect memory. Ask "is Sam on the guest list?" and the bouncer can say "definitely not" (then you don't waste time going in) or "maybe — go check". It never wrongly turns away a real guest (no false negatives), but it occasionally waves through a stranger (a false positive). That trade is exactly what we want: a cheap, certain no saves an expensive disk read.

It works with a bit array and a few hash functions. To add a key, hash it k different ways and set those bits to 1. To test a key, hash it the same ways: if any of those bits is 0, the key was never added — a guaranteed no. If all are 1, it's probably present (or a rare collision — a false positive).

KiwiDB sizes each filter from two numbers — n (expected keys) and fpr (target false-positive rate, default 1%) — using the standard formulas:

# bits needed and number of hash functions (optimal)
m = -n · ln(fpr) / (ln 2)²      # bit-array size
k = (m / n) · ln 2              # how many hashes per key

For example, 1,000,000 keys at 1% gives about 9.6 million bits (~1.2 MB) and 7 hash functions. The hashes come from mmh3 (MurmurHash3 — fast and well-spread); each bit is set with simple byte arithmetic (bits[i>>3] |= 1 << (i&7)).

★ If the examiner asks…

"Can a bloom filter ever say a key is present when it isn't?" → Yes — that's a false positive, and it only costs a wasted lookup. "Can it ever say absent when the key is present?" → Never. No false negatives. That asymmetry is the entire reason it's safe to use as a read filter.

3.6 · The sparse index — jump near the key, not to it

per SSTable  app/index/sparse.py

Once the bloom filter says "maybe", the reader needs to find where in the big data file the key sits. A dense index (one entry per key) would be huge — as big as the data itself. Instead KiwiDB keeps a sparse index: just the first key of each block and that block's byte offset.

To find a key, a binary search (bisect) finds the largest first-key that is ≤ your key — that's the one block that could contain it. The reader then scans only that single ~4 KB block. So a tiny index (one entry per block, not per record) narrows millions of records down to one block.

Need

Find a key's block without an index as large as the data.

Benefit

Index size is O(number of blocks), not O(number of records) — small enough to cache entirely in memory.

Cost

You scan one whole block instead of jumping to the exact record — a cheap, bounded price.

3.7 · The three-tier block cache

in memory  app/cache/block.py

Reading from disk is slow, so KiwiDB keeps recently-used pieces in RAM using an LRU (least-recently-used) cache. The twist: it's three independent caches, one each for data blocks, sparse indexes, and bloom filters.

◆ Why three caches instead of one?

Bloom filters and indexes are tiny and used on every lookup; data blocks are large and used less evenly. If they shared one cache, a flood of big data blocks could evict the small, precious filters. Separate caches with separate size limits mean each tier protects its own — a clean example of designing for the access pattern.

(Implementation detail worth knowing: the filter and index are stored under reserved "sentinel" cache keys, −1 and −2, so they never collide with real block offsets, which are always ≥ 0. When compaction deletes a file, its entries are flushed from all three caches.)

3.8 · The k-way merge iterator — the heart of compaction

app/common/merge_iterator.py

Compaction must merge several already-sorted SSTables into one sorted stream. That's the classic k-way merge: keep the current smallest record from each input in a min-heap, repeatedly pop the global smallest, and refill from whichever input it came from. Merging M records across N inputs costs O(M log N).

Two rules run during the merge and are pure exam gold:

  • Deduplication by version. The heap orders equal keys so the highest sequence number comes out first. The merge emits that newest version and skips the older duplicates of the same key.
  • Tombstone garbage collection. A delete-marker (tombstone) must linger long enough to shadow the value in deeper levels. So a tombstone is dropped only once its sequence number is below a seq_cutoff (meaning no older data could still need shadowing); above the cutoff it is kept.

3.9 · The supporting cast: versions, IDs and locks

Sequence numbers (MVCC)

Every write gets a monotonically increasing sequence number. Newer = higher. This is how KiwiDB knows which of two copies of a key is the live one — highest seq wins. It's a lightweight form of MVCC: old versions coexist until compaction removes them.

UUIDv7 file IDs

SSTable folders are named with UUIDv7, which embeds a millisecond timestamp in its high bits. Sorting the IDs alphabetically therefore sorts them by creation time — handy for recovery and for finding the newest L0 tables, with no extra bookkeeping.

Async reader-writer lock

For state that's read often and changed rarely (like the set of live SSTables), an AsyncRWLock lets many readers run together but gives a writer exclusive access. It uses writer preference so a steady stream of readers can't starve a waiting writer.

★ If the examiner asks…

"How does KiwiDB handle two writes to the same key?" → Both are stored, each with its own sequence number; reads return the one with the highest seq; compaction later discards the loser. Nothing is ever overwritten in place — consistent with the append-only philosophy.

04

Operation flows — what actually happens

Now we trace the four operations end-to-end. If you can narrate these out loud, you can explain the whole project. Step through each figure with Next ▶ and read the highlighted step as you go.

4.1 · Writing a key (put)

  1. Assign a sequence number. The engine stamps the write with the next monotonic seq, fixing its version.
  2. Append to the WAL. The record is written to the on-disk log first. This is the durability point — survive past here and a crash can't lose the write.
  3. Insert into the active memtable under a short write-lock on the skip list.
  4. Acknowledge to the caller. Done — typically sub-millisecond.
  5. Maybe freeze. If the memtable is now over its threshold, it's frozen and queued for flushing while a new empty one takes over.

4.2 · Reading a key (get)

Reads are the harder direction in an LSM tree — a key could be in the memtable or in any level — so KiwiDB checks newest to oldest and stops at the first hit (which, by construction, is the live version).

4.3 · Deleting a key — the tombstone

You can't erase a key from an immutable file, so a delete is just a special write: a record whose value is a tombstone marker, stamped with a fresh (higher) sequence number. On read, that newer tombstone shadows any older value — the key reads as "not found". The dead value and, eventually, the tombstone itself are physically removed later, during compaction.

★ If the examiner asks…

"Why keep a tombstone at all — why not just drop the key?" → Because the old value still exists in deeper levels. The tombstone must survive long enough to shadow those copies during reads and merges. Only when compaction is certain no older copy remains (seq below the cutoff) is the tombstone itself discarded.

4.4 · Flushing — parallel writes, ordered commits

When frozen memtables pile up, the flush pipeline writes them to L0 SSTables. It wants two things that seem to conflict: speed (write several tables at once) and correctness (the on-disk order of versions must match the order they were written). KiwiDB's answer is a clean two-phase design.

◆ Why bother ordering the commits?

Two flushed tables might contain different versions of the same key. If they became visible out of order, a reader could momentarily see an older value win. Serializing the commit step guarantees on-disk visibility follows write order — correctness — while still getting the speed of parallel writes. It's "parallelism where it's safe, ordering where it matters".

4.5 · Compaction — the background tidy-up

Compaction merges overlapping/old SSTables into fewer, tidier ones a level down. It's triggered after flushes when a level has too many files (L0) or grows too big (L1+). The merge itself is the k-way merge from §3.8, and it does the real cleanup: dropping superseded versions and expired tombstones.

While the merge runs, the old input tables stay readable (a reference count keeps them alive until in-flight reads finish). When the new table is ready, the engine atomically swaps it in, marks the inputs for deletion, and clears their cache entries. Crucially, the heavy merge runs in a separate process — the subject of the next section.

"What guarantees you don't lose data on a crash?" → The WAL is written before the memtable, every frame is CRC-checked, SSTables only count as complete once meta.json is written last, and recovery replays the WAL while skipping already-flushed entries. Durability comes from ordering (log first) plus integrity checks (CRC) plus atomic completion markers (meta.json).

05

Parallel execution: process pools and the GIL

This is one of the most distinctive engineering decisions in KiwiDB, and a classic viva topic for a Python project. To explain it you first need the GIL.

What is the GIL, and why does it get in the way?

CPython has a Global Interpreter Lock (GIL): a single lock that lets only one thread run Python bytecode at a time, per process. So even on an 8-core CPU, eight Python threads doing heavy computation don't run truly in parallel — they take turns holding the one lock.

▪ In plain words — the one-pen analogy

Imagine an office where everyone must share a single pen to write. It doesn't matter how many people (threads) you hire — only one can write at any instant. Threads are great when people spend most of their time waiting (for disk, network) and only occasionally need the pen. They're useless for getting more writing done in parallel. To truly write in parallel, you need more pens — that means more processes, each with its own GIL.

Why compaction specifically needs a second process

Most of KiwiDB's work is I/O-bound — waiting on disk — and asyncio handles that beautifully (more on that below). But compaction is CPU-bound: it decodes thousands of records, recomputes checksums, re-hashes keys into a new bloom filter, and runs the k-way merge. That's pure Python computation that holds the GIL the whole time. If it ran in the main process, it would freeze every other read and write for the duration.

So KiwiDB ships the merge off to a separate process, where it has its own interpreter and its own GIL, running on a different CPU core — while the main process keeps happily serving requests.

How it's wired in code

The compaction manager hands the merge to a ProcessPoolExecutor, and wraps that blocking call in asyncio.to_thread so the event loop itself never stalls waiting for it:

# app/engine/compaction_manager.py — run the merge off the main process
def _run_in_subprocess(task):
    with ProcessPoolExecutor(max_workers=1) as pool:
        return pool.submit(run_compaction, task).result()

# called as:  await asyncio.to_thread(_run_in_subprocess, task)
# → event loop stays free; the merge runs in a child process
◆ Why the task is "just data"

To send work to another process, Python must pickle (serialize) it and ship it across the process boundary. So the CompactionTask contains only primitive values — file IDs, directory paths, levels, a sequence cutoff. No open files, no locks, no live objects. The subprocess opens the files itself from those paths, does the merge, and returns just the metadata of the new table. Designing the task as plain, picklable data is what makes the whole scheme possible.

Two kinds of "at the same time" — don't confuse them

An examiner may probe whether you understand the difference. KiwiDB uses both, for different problems:

asyncio concurrency (one core)

For I/O-bound work — waiting on disk reads/writes. Many operations overlap their waiting on a single thread. The parallel SSTable writes in the flush pipeline use this. It does not beat the GIL for computation; it just stops you wasting time idle.

multiprocessing parallelism (many cores)

For CPU-bound work — the compaction merge. A separate process means a separate GIL and a separate core, so computation truly runs in parallel with the main process.

KiwiDB even detects its environment at startup (_detect_parallelism_mode): on a future GIL-free Python build (3.13+ "free-threaded") it could use threads for the merge; on standard Python 3.12 it falls back to multiprocessing. The code is written to take advantage of whichever it's running on.

★ If the examiner asks…

"Why not just use threads for compaction?" → Because compaction is CPU-bound, and the GIL means Python threads can't execute bytecode in parallel — they'd just take turns, giving no speed-up and still freezing the main loop. A separate process has its own interpreter and GIL, so the merge runs on another core while the database stays responsive.

06

B+ tree vs LSM tree

Almost every database uses one of these two structures, and "why did you choose an LSM tree?" is the question most likely to decide your viva. So know the contrast cold.

How a B+ tree works (the other camp)

A B+ tree is a balanced, sorted tree of fixed-size pages. Internal pages hold keys that route you down; all real data sits in the leaf pages, which are linked together in sorted order. A lookup walks from the root down to a leaf — a handful of page reads, always the same shape. It's the structure behind MySQL/InnoDB, PostgreSQL, SQLite and most relational databases.

The defining trait: updates happen in place. To change a key, you find its leaf page and rewrite that page where it sits on disk. If a page overflows, it splits into two and the parent is updated. This keeps reads tight and predictable — but every write is a random-access write to a specific spot on disk.

Complexity, operation by operation

Here n is the number of keys and b the page branching factor of a B+ tree. The headline numbers look similar — the real story is in the type of I/O (random vs sequential), which the notes call out.

▪ The one-sentence summary

B+ trees turn writes into random I/O to keep reads cheap; LSM trees turn writes into sequential I/O and pay for it later with compaction. Modern SSDs and write-heavy workloads (logs, metrics, events) tilt that trade toward LSM — which is exactly KiwiDB's target.

So when would you pick each?

Choose a B+ tree when…

Reads and range queries dominate; you need predictable low read latency; the workload is classic transactional/relational. Examples: MySQL (InnoDB), PostgreSQL, SQLite.

Choose an LSM tree when…

Writes/ingest dominate; you're on SSDs that love sequential writes; you can tolerate background compaction and slightly costlier reads. Examples: Cassandra, RocksDB, LevelDB, HBase — and KiwiDB.

★ If the examiner asks…

"Your project is write-optimised — what did you give up, and how did you claw it back?" → We gave up cheap reads and clean space (higher read & space amplification). We claw reads back with bloom filters + a block cache + a sparse index, and we claw space back with compaction. That's the honest, complete answer.

07

Concurrency & correctness

KiwiDB is async-first: many operations are in flight at once. Correctness comes from choosing the smallest lock that's safe for each piece of shared state, plus a few invariants that make crashes harmless.

The locking map

Notice there's no single global lock — each structure guards itself with the lightest mechanism it can:

Shared stateProtected byWhy this choice
Skip-list nodesPer-node locks; lock-free readsWriters touching different keys don't block each other; reads never lock at all
Memtable size/countTiny dedicated locksCounters update atomically without locking the whole table
Set of live SSTablesAsync reader-writer lock (writer-preferred)Read-heavy, rarely changed; many readers, occasional exclusive writer
SSTable file lifecycleReference-counted registryA file being compacted away isn't deleted until in-flight reads finish
Flush commit orderPer-slot events (the "event chain")Writes parallelise; commits serialise — visibility matches write order
Which level is compactingLevel "reservation" setTwo compactions never touch the same level at once

The invariants that make a crash a non-event

  • Log before memtable. Nothing is acknowledged until it's durable in the WAL.
  • Checksums everywhere. Every WAL frame and every SSTable record carries a CRC32, so corruption or truncation is detected, never silently served.
  • meta.json written last. An SSTable counts as "complete" only when its metadata file exists. A crash mid-write leaves an incomplete folder that recovery simply ignores.
  • Atomic swaps. WAL truncation and compaction's file replacement publish their result in one atomic step, so a reader sees either the old world or the new — never a half-built one.
  • Versions, not overwrites. Because data is only ever appended with a higher sequence number, there's no in-place state to corrupt.
◆ Why it matters

These five rules together give KiwiDB its headline property: crash-safety. You can kill the process at any instant and it restarts in a consistent state with no acknowledged write lost. That's the difference between a toy and a real storage engine — and a great thing to state plainly in a viva.

The public API — small on purpose

Everything above sits behind six async methods. This is the whole contract a user sees:

engine = await LSMEngine.open(data_root)   # open or recover
await engine.put(key, value)              # write / update
value = await engine.get(key)            # read (None if absent/deleted)
await engine.delete(key)                   # tombstone
await engine.flush()                       # force memtable → disk
await engine.close()                       # flush + release everything
▪ In plain words

All the machinery — WAL, skip list, flushing, compaction, caching — is hidden behind put/get/delete. A clean, minimal public surface over rich internals is itself a design quality worth pointing out.

Examiner Q&A bank

Real questions an external examiner is likely to ask, with crisp model answers. Click a question to reveal its answer and try to answer first — then check yourself.

LSM fundamentals

Q1 What is an LSM tree in one sentence?

A storage structure that buffers writes in a sorted in-memory table, flushes them to immutable sorted files on disk, and periodically merges those files in the background — trading slightly costlier reads for very fast, sequential writes.

Q2 Why is it called "log-structured"?

Because data is only ever appended — like a log — never modified in place. New values and delete-markers are added; the structure is a merge of these append-only layers.

Q3 Name three real databases that use LSM trees.

Cassandra, RocksDB, LevelDB, HBase, ScyllaDB — any of these. They're the standard choice for write-heavy workloads.

Q4 What are read, write and space amplification?

Write: how many times one logical write is physically re-written (flush + each compaction). Read: how many places you may check to answer one read (memtable + levels). Space: extra disk held by dead versions and tombstones before compaction reclaims it. LSM trees have higher amplification on all three than a B+ tree but win on write throughput because the writes are sequential.

Memtable & skip list

Q5 Why a skip list and not a hash map for the memtable?

The memtable must stay sorted so it can be flushed straight into a sorted SSTable and so range scans work. A hash map gives O(1) lookup but no order. A skip list gives O(log n) lookup and keeps keys ordered, with easy concurrency.

Q6 Why a skip list rather than a balanced BST (AVL / red-black)?

Same O(log n) search, but far easier to make concurrent. Insertion only relinks a few forward pointers, so fine-grained per-node locking and lock-free reads are straightforward. Balanced trees need rotations that ripple through the structure and are painful to lock correctly.

Q7 How does the skip list avoid deadlock with many writers?

Every insert acquires its node locks in a fixed global order (ascending Python id()). Consistent lock ordering is the classic guarantee that a cycle of "A waits for B, B waits for A" can never form. It also validates predecessors after locking and retries on a rare conflict (optimistic concurrency).

Q8 How can reads be lock-free while writes take locks?

A new node is linked into the lower levels first and only marked fully_linked as the final step. Readers just follow pointers and treat a not-yet-fully-linked node as not present, so they never observe a half-built node and never need a lock.

Durability, WAL & recovery

Q9 If the memtable is in RAM, how do you not lose data on a crash?

The Write-Ahead Log. Every write is appended to the WAL on disk before it's acknowledged, so a crash can be recovered by replaying the log on startup.

Q10 Walk me through recovery.

Restore the sequence counter from the highest seq already on disk → replay the WAL frame by frame, verifying each CRC → skip any entry whose seq is already covered by a flushed SSTable → load the remaining (unflushed) entries into a fresh memtable. The engine is now in exactly its pre-crash state.

Q11 Why is meta.json written last in an SSTable?

It's a completeness marker. The data, index and filter files are written first; only when all are safely on disk is meta.json written. If a crash interrupts the write, there's no meta.json, so recovery treats the folder as incomplete and ignores it — no corruption.

Q12 What is the CRC32 for?

Integrity. Every WAL frame and SSTable record stores a checksum. On read, KiwiDB recomputes it; a mismatch means corruption or a crash-truncated tail, so it stops/skips rather than returning garbage.

SSTables, bloom filters & caching

Q13 Trace exactly what happens on a read that misses the memtable.

For each SSTable, newest first: check the bloom filter — if "no", skip the whole table. If "maybe", use the sparse index to find the one block that could hold the key, fetch that block from the cache or via mmap from disk, and scan it. Return the highest-seq match; a tombstone means "not found".

Q14 Can a bloom filter be wrong?

It can produce false positives ("maybe present" when actually absent), which only cost a wasted lookup. It can never produce a false negative — if it says "absent", the key is definitely absent. That one-sided error is why it's safe as a read filter.

Q15 How do you size a bloom filter?

From the expected key count n and target false-positive rate p: bits m = -n·ln(p)/(ln2)² and hash count k = (m/n)·ln2. Lower p ⇒ more bits and more hashes.

Q16 Why a sparse index instead of indexing every key?

A dense index would be nearly as large as the data. The sparse index stores only the first key + offset of each block, so it's O(number of blocks) — small enough to keep in RAM. You binary-search it to the right block, then scan that one ~4 KB block.

Q17 Why three separate caches?

So a flood of large data blocks can't evict the tiny, frequently-used bloom filters and indexes. Independent LRU caches with their own size limits let each tier protect what it needs.

Compaction

Q18 What problem does compaction solve?

Without it, files accumulate forever: reads check more and more tables (read amplification) and the disk fills with dead versions and tombstones (space amplification). Compaction merges files, drops superseded versions and expired tombstones, and keeps the level structure tidy.

Q19 How does the merge work, algorithmically?

A k-way merge using a min-heap over the sorted inputs, O(M log N) for M records across N inputs. Equal keys are ordered newest-first, so the merge emits the newest version and skips older duplicates.

Q20 When is a tombstone deleted?

Only when compaction is sure no older copy of the key can still exist beneath it — i.e. its sequence number is below the seq_cutoff. Until then the tombstone is preserved so it keeps shadowing older values in deeper levels.

Q21 What stops an SSTable being deleted while a read is using it?

A reference-counted registry. A file marked for deletion after compaction is only physically removed once its reference count hits zero — i.e. all in-flight reads have finished.

Parallelism & the GIL

Q22 What is the GIL and why does it matter here?

CPython's Global Interpreter Lock lets only one thread execute Python bytecode at a time per process. So CPU-bound work (like compaction) can't be sped up with threads, and would block everything else if run on the main process.

Q23 How does KiwiDB get true parallelism for compaction?

It runs the merge in a separate process via ProcessPoolExecutor, wrapped in asyncio.to_thread so the event loop isn't blocked. The child process has its own interpreter and GIL and runs on another core, while the main process keeps serving reads and writes.

Q24 Why must the compaction task contain only plain data?

Because it's pickled and sent across a process boundary. It carries file IDs, paths, level, and a seq cutoff — no open file handles or locks. The subprocess re-opens the files itself and returns just the new table's metadata.

Q25 Difference between asyncio concurrency and multiprocessing here?

asyncio overlaps I/O waits on one core (used for parallel SSTable writes during flush). multiprocessing gives real multi-core CPU parallelism (used for the compaction merge). Different tools for I/O-bound vs CPU-bound work.

B+ tree vs LSM & design

Q26 Core difference between a B+ tree and an LSM tree?

A B+ tree updates data in place (random-access writes) to keep reads cheap. An LSM tree only ever appends (sequential writes) and defers cleanup to background compaction. B+ favours reads; LSM favours writes.

Q27 Why is sequential I/O faster, even if you write more bytes?

No disk seeking, and the OS/SSD can batch sequential writes efficiently. LSM converts many small random writes into a few big sequential ones, which is a big net win on modern hardware — even though the total bytes written (write amplification) is higher.

Q28 Given LSM has worse read amplification, why are your reads still fast?

Three mitigations stack up: bloom filters skip almost every table without disk I/O; the sparse index pinpoints one block; and the block cache keeps hot blocks, indexes and filters in RAM. Together they bring real-world reads close to a single lookup.

Q29 Why did you choose an LSM tree for this project?

To build a write-optimised, crash-safe engine from scratch and learn database internals deeply: WAL durability, concurrent in-memory structures, on-disk file formats, background compaction, and Python concurrency around the GIL. The LSM design exercises all of these.

Q30 What would you improve or add next?

Good honest answers: leveled (size-tiered vs leveled) compaction tuning, block compression, a manifest/checkpoint to speed recovery, range-scan iterators exposed in the API, or per-key TTL. Showing you know the limits earns credibility.

The 5-minute recap & glossary

Explain the whole project in one breath

If you can say this aloud, you're ready:

▪ The end-to-end story

"KiwiDB is a key-value store built on a log-structured merge tree. A write is first appended to a write-ahead log on disk for durability, then inserted into an in-memory, sorted skip-list memtable — so writes are fast and crash-safe. When the memtable fills, it's frozen and flushed to an immutable, sorted SSTable in level 0; flushes write in parallel but commit in order. Reads check the memtable, then each SSTable newest-first, using a bloom filter to skip tables, a sparse index to find the block, and a cache to avoid disk. In the background, compaction merges tables down through the levels, dropping old versions and tombstones — and it runs in a separate process to dodge Python's GIL and keep the database responsive. The whole thing favours fast sequential writes, paying for it with background work, which is exactly the right trade for write-heavy workloads."
